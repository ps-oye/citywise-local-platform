# Phase 6: SEO, analytics and deployment

Phase 6 keeps the existing HTML/CSS/vanilla JavaScript, Supabase and Cloudflare Pages stack. The selected release target is a **noindex preview using the existing development database**, not a production launch. Development business/demo data and the administrator are retained.

## Public pages and search metadata

Homepage, category, explore, search and merchant URLs now return useful database-backed HTML before JavaScript. Search forms and previous/next listing pages work without JavaScript. Public requests use only the publishable key under RLS; SEO rendering never uses the privileged checkout client. Newly published listings appear at their canonical URL without a rebuild. Draft/disabled/missing content returns a real 404; catalog failures return a safe 503.

Metadata is shared by server rendering and browser navigation: title, description, canonical URL, Open Graph, Twitter card and safely encoded JSON-LD. Structured data contains the actual visible business/context and no invented ratings, reviews, sales, prices or availability. Fictional merchants do not emit a real-business entity. Weekly hours are omitted during active manual/special overrides; midnight 24-hour schedules use Google's documented representation. Ambiguous non-midnight all-day shifts are omitted from schema rather than inferred.

Preview, demo, filtered/search/explore and error pages stay noindex. Indexing requires all of the following at runtime: `DEPLOYMENT_ENV=production`, `SITE_INDEXING_ENABLED=true`, a configured HTTPS `SITE_URL` (or matching build `VITE_SITE_URL`), and a request to that exact origin. Eligible real content is also required for page indexing. Admin HTML always remains noindex and requires the existing database-authorized login for its data.

`/robots.txt` is generated by the Pages Function. Crawlers may read page-level noindex directives; robots disallow alone is not an indexing control. A production sitemap declaration appears only when indexing is enabled. `/sitemap.xml` indexes `/sitemaps/0.xml`, `/sitemaps/1.xml`, etc., with at most 1,000 URLs per page and a one-million-URL guard. Sitemap queries include eligible real city/category/canonical merchant URLs, exclude demos and use the same visible-category precedence as merchant routing. No inaccurate `lastmod` is invented for listings whose child catalog/hours may have changed.

Open Graph uses the original repository-owned 1200 × 630 brand card or a stable `/media/{uuid}` URL for an eligible business image. That endpoint rechecks public visibility and downloads with public credentials/RLS; private/draft/disabled media never becomes public through an admin credential. Responses are no-store, and the Storage buckets stay private. The share artwork is reproducible from `public/images/share-card.svg` using `scripts/create-share-card.mjs` and the installed browser; normal builds use the existing PNG and need no browser for asset generation.

## Activity and enquiry reporting

Open `/admin/` → **Enquiries & analytics**. Choose a city and a range of up to 90 days. Quick ranges cover 7, 30 or 90 days, using the city's timezone. The default excludes fictional demo activity; the checkbox makes sample activity explicit.

The report includes listing views, phone/directions/WhatsApp link clicks, qualified visible promotion impressions, promotion clicks and CTR, zero-filled daily trends, top ten listings/promotions and the latest twenty relevant enquiry references/states. The overview also shows the last 30 days of non-demo listing views and WhatsApp link clicks. Date/filter controls are locked while a report loads; switching cities replaces the active workspace before new actions can use it.

Browser events are approximate activity reports, not unique visitors or audited advertising figures. Repeated clicks can make CTR exceed 100%; with no impressions it is shown as unavailable. A listing view is reported after successful browser rendering, once per navigation. Server rendering, crawlers, prefetched content and mere database presence do not count as views/impressions. An ad qualifies only after its loaded, active slide is at least 50% in the viewport continuously for one second while the document is visible and no application modal covers it. Slide changes, failed/placeholder images, tab hiding, modals and cleanup reset qualification; each ad qualifies once per page view.

Checkout initiation and handoff preparation are counted independently from the existing trusted checkout records, using their own timestamps. A prepared link does not establish a sent message, accepted order or sale. Analytics responses contain no enquiry notes, customer contacts or item snapshots.

Optional events use the same-origin `/api/events` endpoint, service-only database functions, strict 8 KiB / 20-event limits and separate persistent event budgets. Event identity/type/target are the only accepted browser fields; SQL derives city, associations and time and verifies current publication/contact eligibility. Identical event-key retries count once; conflicting reuse fails atomically. Event quotas are charged before recording and cannot consume checkout budgets.

Event rows store no IP, visitor/session identifier, query, referrer or user agent. Daily domain-separated HMAC fingerprints live only in ephemeral limiter counters, pruned after two days of inactivity. The browser queue is memory-only, capped at 100 events, and retries retain event identities. Do Not Track, Global Privacy Control and the footer's **Privacy & analytics preferences** opt-out suppress future optional activity. Only the opt-out boolean is persisted, with no visitor identifier. Discovery/cart/checkout continue to work when analytics is disabled or unavailable.

Raw event reports currently retain their timestamps/type/business references; no automatic event or enquiry purge is installed. Before production, choose an operational retention period and have a trusted operator review any cleanup transaction. Expired limiter pruning is separate from business/event retention.

## Local verification and performance

```powershell
npm.cmd ci
npm.cmd run verify
$env:PLAYWRIGHT_CHANNEL = 'chrome' # use installed Chrome if downloaded Chromium is blocked
npm.cmd run test:e2e
npm.cmd run pages:functions
npm.cmd run performance
```

`verify` checks syntax, executes actual PostgreSQL/RLS unit/integration fixtures and builds both entry points. Browser tests use isolated Auth/Storage/HTTP fixtures with the actual SQL; no test needs live credentials. The performance command builds a separate fixture frontend, starts an isolated SQL API on 54339 and the real local Cloudflare Pages runtime on 8788, checks its routes, runs Lighthouse for home/category/merchant on simulated mobile/desktop, writes HTML/JSON under ignored `artifacts/lighthouse/`, and stops its owned processes. The default Playwright API remains on 54329. Set `CHROME_PATH` if Chrome Launcher cannot find an installed browser.

Performance improvements include initial public bootstrap reuse, lazy admin analytics/import code, bounded reads, eager/high-priority hero images, optimized existing WebP assets and immutable caching of hashed assets. Static images/icons bypass Functions; dynamic content and private/admin data are not cached publicly. CSP includes only the validated configured Supabase origin when a custom/local origin needs it; no unrestricted source or unsafe-inline allowance is added.

See [the phase report](phase-6-report.md) for actual measurements. Preview SEO measurements deliberately reflect the requested noindex policy; production search eligibility must be verified against the eventual real deployment and content.

## Cloudflare preview deployment

The pinned Wrangler CLI compiles the repository's Pages Functions, not a static-only upload. `wrangler.jsonc` defines `rawatbhata-one`, the `dist` directory, compatibility date, runtime flag and separate preview/production defaults. Both keep indexing disabled until explicitly configured. `_routes.json` excludes hashed assets, images/icons and admin static HTML, while public HTML, robots/sitemaps, media and protected APIs still invoke Functions.

1. Sign in locally with `npx.cmd wrangler login` using Cloudflare's browser flow. Keep passwords/API tokens private. If the account has several Cloudflare accounts, set the intended `CLOUDFLARE_ACCOUNT_ID` in your shell; `.cloudflare.env.example` lists reference names and is not loaded automatically.
2. Preserve the existing `.env.local` and ignored `.dev.vars`. The preview uses the same development Supabase URL/public key, server-only secret/service-role key and at least 32-character checkout HMAC. An optional distinct analytics HMAC also needs at least 32 characters. No secret belongs in a `VITE_` variable.
3. Review/apply only pending Phase 6 migrations in the intended development project, as recorded in the setup/report. Migrations 8 and 9 are already applied to the configured development project; do not replay them or reseed existing catalogs.
4. Run `npm.cmd run deploy:check` after building, then `npm.cmd run deploy:preview`. The command runs verification/build, checks artifacts for server-secret leakage, verifies public schema and server credentials using read-only RPCs, selects a single verified Cloudflare account, and reads raw project metadata including its production branch.
5. The script creates the named Pages project only if it is absent, with production branch `main`, then uses the separate `phase-6` preview branch. It refuses a branch that is the project's production target. Runtime bindings are uploaded to the **preview environment only**, through stdin from memory, with token/value redaction. The CLI's display-oriented project-list JSON is not used to infer safety-critical project metadata.
6. The literal returned immutable preview URL and deployment metadata are saved in ignored `artifacts/preview-deployment.json`. Verify homepage/category/merchant HTML, robots/sitemap, headers, admin login in your own browser and demo checkout restrictions at that URL. Local configuration alone does not prove a hosted deployment.

The script supports a reviewed project name in `wrangler.jsonc` and matching optional `PAGES_PROJECT_NAME`, plus `PAGES_PREVIEW_BRANCH`. It uses normal Wrangler authentication, captures deployment credentials in process memory without writing them to project files, and does not stage/commit/push this repository. Wrangler retains its normal authenticated profile. Existing project audience/domain/production deployments are not deliberately changed. A preview URL is publicly reachable unless separate Cloudflare Access is configured; noindex controls search indexing, not authentication. `node scripts/smoke-preview.mjs` checks the saved preview's public HTML, metadata, asset caching, admin boundary and protected API responses without business-data writes.

## Production preparation

Production remains a separate requested action. Prepare a separate Supabase project with migrations through 9, the private buckets/policies, disabled signup/anonymous sign-in and the manually provisioned single administrator. Configure its public browser values and matching private server values without changing the preview's credentials. Run `npm.cmd run production:check` with the intended `PRODUCTION_SUPABASE_PROJECT_REF` and matching HTTPS `SITE_URL` / `VITE_SITE_URL`; the current development database is explicitly rejected as a production target.

Onboard verified real businesses and images, review/remove or reassign sample data deliberately, configure actual contacts/hours, choose retention/backups, and run the documented QA against that environment. The production check rejects missing real sitemap content or a default city still containing demo content. No seed removal, production database creation, domain purchase or production release happens automatically.

For Cloudflare, set the actual production runtime bindings and canonical origin under the intended production environment; keep preview bindings separate. The build command is `npm run build`, output `dist`, Node 24, with `functions/` from this repository. A Direct Upload project and Git-integrated Pages project are different hosting choices; this flow uses reviewed direct upload and does not create a Git integration. Configure Auth site/allowed redirect URLs for any later email flows, verify real password login and Storage HTTP behavior, and test Cloudflare headers/routing at the final origin. Enable production indexing only after those checks and real content are ready; then validate rich results and submit the sitemap in the domain owner's Search Console.
