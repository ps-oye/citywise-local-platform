# Phase 3 implementation plan and boundaries

Phase 3 extends the existing vanilla-JavaScript discovery application. Full merchant URLs use `/:city/:category/:listing`, resolve current or historical slugs in PostgreSQL and reuse one page renderer. Public cards and search results link to those URLs; existing quick-look links remain compatible. Pages Functions expose meaningful merchant HTML for direct requests, with public credentials under RLS, while Vite uses the same server adapter during development.

Public bounded security-invoker RPCs provide merchant context, paginated catalogs, selected cart products and authoritative cart quotes. Banners, gallery, business information, relevant offerings, service areas and opening schedules come from Supabase. Products support search, dietary/category/availability filters and sorting. Demo-only catalogs may use constrained local licensed assets; real uploaded media remains private.

Business status is calculated in PostgreSQL from IANA-local dates, split/overnight weekly schedules, special dates and active manual overrides. Checkout uses the same database status calculation. Closed merchants remain accessible; permitted closed-hours enquiries are explicitly labeled. No inventory or message-delivery status is inferred.

Carts store bounded product IDs, quantities and last-seen display snapshots in versioned per-merchant localStorage records. Storage is untrusted and optional; current catalog/quote responses determine availability and prices. The confirmation dialog displays an authoritative quote before requesting a handoff, and price/availability changes require review again.

The trusted boundary is a same-origin Cloudflare Pages `/api/checkout` handler, also hosted through a local-only Vite adapter. Privileged Supabase credentials live in server bindings or an ignored `.dev.vars` file, never browser configuration. Requests have strict origin, JSON, size and input checks. Hosted identity uses the ingress address under [Cloudflare's documented header semantics](https://developers.cloudflare.com/fundamentals/reference/http-headers/); local identity comes from the socket. A keyed daily fingerprint supports persistent PostgreSQL request limits without retaining raw addresses. Rate consumption commits separately from business validation, so rejected requests also count.

Service-only transactional RPCs recheck publication, verified non-demo contact, enabled actions, fulfilment, schedule status and every product. They recalculate prices, compare the confirmed quote, serialize idempotency keys and snapshot line names/units/prices. The endpoint prepares the WhatsApp link from verified database values, records link preparation and returns a fallback link if automatic navigation is blocked. Recorded states remain initiation and handoff creation, never message sent/order accepted/completed.

Implementation order: additive migration and SQL tests; cart/formatting rules and tests; shared merchant renderer and page controller; trusted checkout/SSR adapters; richer fictional catalog seed; desktop/mobile integration tests; documentation. Retain the existing discovery regression suite. All automated writes use disposable PostgreSQL fixtures; real demo checkout remains disabled. No admin dashboard, imports, general analytics or production deployment is included.
