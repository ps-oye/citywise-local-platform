# Phase 5 catalog and import architecture

The existing admin entry point gains Products & imports, scoped to one selected commerce/restaurant merchant. It includes bounded catalog search, manual product/category editing, product image selection from that merchant's media library, template downloads, XLSX worksheet selection, CSV/XLSX validation, a paged change preview, explicit confirmation and persistent import history with row/column errors. Existing public catalog and checkout reads remain authoritative and require no source changes for new products.

File parsing stays in a disposable same-origin module worker. The pinned read-excel-file parser handles Excel cell values, Papa Parse handles CSV records, and fflate provides bounded ZIP inspection and template packaging. XLSX preflight enforces ZIP size/entry/coordinate limits and rejects formulas, macros, external relationships and malformed XML before parsing; cached formula values are never accepted. Parsing work can be cancelled/timed out. Formula-safe CSV exports protect downloaded reports. No spreadsheet file is executed or uploaded to public Storage.

The browser performs helpful validation; PostgreSQL independently validates the normalized row payload. A new forward migration supplies authenticated security-invoker public RPCs guarded by the existing allowlist, plus narrow private security-definer helpers for private import records. Existing table policies stay enabled; no broad private write grants are given to browser roles. Private staging is a bounded immutable import artifact rather than the public catalog's source of truth.

Preparing an import records its merchant, actor, mode, file metadata, canonical rows, field errors, server-derived change classification and catalog snapshot. No product is changed during preview. Confirmation accepts the prepared job identity rather than new browser prices. It locks the merchant, rechecks the actor and snapshot, applies SKU-based changes in one transaction and records a catalog version/report. Retries of the same prepared job are idempotent. Stale previews fail and must be reviewed again. Failed application rolls back every product change while retaining a failure report.

Insert/update requires SKU, product name and price, preserves existing omitted optional fields, and uses documented defaults for new rows. Blank optional values explicitly clear nullable fields or use documented defaults where applicable; a blank category/image clears that association. Category references resolve only inside this merchant. Price-only mode accepts only SKU/price (and optional original price), rejects unknown SKUs and changes no other fields. Missing products are always untouched. Archive/restore is explicit; imports never silently restore archived products. Manual editing uses row revisions and the same constraints. Full replacement/deletion is excluded.

The implementation followed the initial order: parser/security inspection; migration and transactional authorization tests; domain/worker/file limits; catalog/import/report screens; desktop/mobile regression and visual checks; additive development migration; documentation and results. Phase 6 is excluded. See [catalog guide](catalog-guide.md), [setup](phase-5-setup.md) and [verification results](phase-5-report.md).

## Modules and limits

`src/admin/pages/catalog.js` is lazy-loaded from the separate admin entry point. Catalog rendering, manual editing and imports are separated into `catalog-ui.js`, `catalog-product-editor.js` and `catalog-imports.js`; `src/data/admin-repository.js` contains only the narrow RPC calls. `src/domain/catalog-import.js` defines canonical headings, limits and helpful validation. The public homepage does not import parser code.

`catalog-file-reader.js` owns a disposable module worker and real timeout/cancellation. `catalog.worker.js` caches only the current file's bounded parse state. `catalog-file-parser.js` checks ZIP central/local metadata, streamed expansion, CRCs, entry paths, XML structure, relationships and ascending cell coordinates before invoking the maintained cell reader. It normalizes XML attribute names the same way as the reader and rejects namespace collisions, preventing the two parsers from inspecting different cells or worksheets. Formulas are rejected before cached values can become ordinary cells. SKU cells must be text; exact price lexemes are validated and converted to minor units in SQL.

The [read-excel-file documentation](https://gitlab.com/catamphetamine/read-excel-file) and its [cell parser](https://github.com/catamphetamine/read-excel-file/blob/master/source/xlsx/parseCell.js) informed the preflight boundary: parsing values alone does not reliably expose formula identity. The [archive reader](https://github.com/catamphetamine/read-excel-file/blob/master/source/zip/unzipFromArrayBuffer.js) can select worker decompression for large compressed entries. After bounded inspection, this application repacks XML with stored entries, so the library runs inside the existing terminable same-origin worker without creating nested blob workers. A strict-CSP browser case exercises a shared-string XML entry over 512 KiB.

`catalog-downloads.js` builds blank styled XLSX templates with text-formatted SKUs and CSV templates without adding a writer framework. Report CSV exports use formula escaping. No input file is executed or uploaded to Storage. The 5 MiB file, 1,000-row, 1 MiB normalized JSON and 16 MiB expanded-workbook limits are deliberately bounded for a small-town catalog; see the guide for the complete contract.

## Database transaction and concurrency

Migration 7 adds a private artifact table, not another product source. Its composite foreign key prevents cross-merchant job references. Public RPCs remain invokers; the four private definer helpers require the active database administrator and handle only preview preparation, job locking/finishing and version recording. All functions have empty search paths; authenticated users still have no private-table write grants.

Preparation locks the merchant and existing target products, checks duplicate SKUs, validates every row, creates deterministic differences, and compares snapshots before/after planning. The immutable plan stores both target product identity and revision, including expected absence for new SKUs. The digest binds merchant, mode, source metadata and canonical values to a request identity and actor. A validation failure persists a failed job/report and performs no product write.

Confirmation takes only the job UUID. It locks merchant → job → target products, shares category/media locks, checks expiry and the server snapshot, and revalidates each row. Each current target must match the preview's product ID and revision. The SKU upsert also constrains its conflict update to that identity/revision, so a concurrent SKU rename or newly appearing row cannot substitute another target. Existing table RLS and cross-merchant foreign keys still apply. The transaction skips unchanged rows and records one catalog version when product changes occur.

The mutation block uses a PostgreSQL exception subtransaction: any later-row failure rolls back all product/version mutations, then records a safe failed report outside that subtransaction. Already settled jobs return their saved result before freshness checks, making retries safe after a lost HTTP response. Admin revocation and actor ownership are rechecked at confirmation. Manual editing shares validation and uses expected row revisions; it records catalog versions and relies on the existing audit trigger.

The UI preserves a job identity for an ambiguous network retry, resets it for a failed job, and prevents late page/file/report callbacks from replacing newer results. Applying disables file/mode, preview, report pagination and confirmation controls. File cancellation cannot cancel a committed database request. Only business catalog data and private source/plan/report metadata are retained; no customer fields or additional credentials are introduced.
